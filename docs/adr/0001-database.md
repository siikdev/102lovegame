# ADR-0001: 데이터베이스 선택 — 로컬 컨테이너를 쓸 것인가?

날짜: 2026-11-07 · 상태: 승인

## 맥락

- 용도: 발로란트 내전 기록 (주 1~2회, 판당 1레코드 + 선수 10명 스탯) — 수년 쌓여도 수천 행 규모
- 사용자: 본인(+ 내전 멤버 열람 가능성), 동시 쓰기 사실상 없음
- 환경: WSL2 로컬 실행이 기본, 외부 호스팅은 미정
- 예정 기능: 스크린샷 기반 결과 기록(파일 저장 + 스탯 추출), **유저별 승률/KD 집계 (맵별·요원별)** ← 관계형 질의가 필요해지는 지점

## 검토한 선택지

| | localStorage (현행) | **SQLite + 경량 백엔드** | PostgreSQL (Docker 컨테이너) |
|---|---|---|---|
| 운영 부담 | 0 | 거의 0 (DB=파일 1개) | 컨테이너·볼륨·포트 관리 |
| 기기/브라우저 간 공유 | ❌ 브라우저에 묶임 | ✅ 서버 경유 | ✅ |
| 승률/KD 집계 (맵/요원별) | JS로 수동 | ✅ SQL 한 방 | ✅ SQL |
| 스크린샷 저장 | ❌ 부적합 | ✅ 파일시스템 + 경로만 DB | ✅ (별도 스토리지 권장) |
| 백업 | JSON 내보내기 수동 | 파일 복사 = 백업 | pg_dump/볼륨 |
| 동시 다중 쓰기 | - | 제한적 (이 규모엔 충분) | ✅ 강함 |

## 결정: 단계적 — **지금은 컨테이너 불필요**

- **Phase 1 (현재)**: localStorage + JSON 내보내기. 목업으로 충분.
- **Phase 2 (백엔드 도입 시)**: **SQLite** (`backend/data/app.db`, better-sqlite3). 컨테이너 없이 Node 프로세스 하나. 이 규모에서 Postgres 컨테이너는 오버엔지니어링 — DB는 라이브러리(SQLite)로 충분하고, 컨테이너는 "DB가 서버 프로세스일 때"만 의미가 있다. 스크린샷은 `backend/uploads/` 파일 + DB엔 경로/메타만.
- **Phase 3 (조건부 전환)**: 아래 중 하나라도 해당되면 Postgres + docker-compose 로 전환:
  1. 외부 서버에 배포해 멤버들이 각자 기록을 쓰기 시작
  2. 동시 쓰기 충돌이 실제로 발생
  3. 서비스가 여러 프로세스/호스트로 분리
  - adapter 인터페이스와 SQL 스키마는 거의 그대로 이전 가능하게 설계한다 (backend/README.md 의 스키마 참고).

## 결과

- frontend 는 이 결정과 무관하게 `data/adapters/` 교체만으로 대응 (이미 구조 반영)
- 전환 비용 최소화를 위해 레코드는 JSON 직렬화 가능 형태 유지, 스키마 버전(schemaVersion) 관리
