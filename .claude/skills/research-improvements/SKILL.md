# /research-improvements — 개선 리서치

목표: "일단 되게" 만든 것들을 그대로 두지 않기. 단, **조사는 좁고 깊게** — 세션당 주제 1~2개, 검색 2~4회로 제한 (end-day 가 무거워지면 안 됨).

## 절차

1. **후보 선정**: 이번 세션 커밋(`git log --oneline` 오늘자) 중 ① 레퍼런스 없이 감으로 만든 UI ② 처음 써본 기술(라이브러리·API) ③ 사용자가 "느낌이 아쉽다"고 한 것. 1~2개만 고른다 — 이미 스킬/가이드 기반으로 만든 것(예: dataviz 거친 차트)은 제외.
2. **조사** (WebSearch 2~4회): 해당 패턴의 통용 베스트 프랙티스, 유사 서비스 사례, 브라우저 API/라이브러리 최신 동향. 출처 URL 확보.
3. **기록**: 조사 결과를 `docs/BACKLOG.md` 에 항목으로 — 양식은 propose-features 와 동일하되 **접근** 란에 출처 링크 포함. 사소한 개선(CSS 몇 줄 수준)이고 확실하면 즉시 적용해도 됨 (배포 금지 지시가 있는 날은 커밋만).
4. **보고**: "조사한 주제 → 결론 한 줄 → 백로그 반영 여부" 형식으로 요약.

## 원칙

- 추측으로 "트렌드"를 말하지 않기 — 출처 없는 개선안은 propose-features 소관
- 유료 솔루션은 무료 대안과 함께
- 같은 주제 재조사 방지: BACKLOG 항목에 조사 날짜 명시
